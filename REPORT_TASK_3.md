# Задача 3

В этой задаче была создана архитектура для конвейерной обработки набора изображений, разделяющая процессы чтения, свёртки и записи. Такой подход позволяет операциям ввода-вывода и вычислениям выполняться одновременно, что максимально утилизирует ресурсы системы и увеличивает общую пропускную способность.

## Архитектура конвейера

Система построена на классическом паттерне **"Производитель-Потребитель"** с тремя основными асинхронными стадиями:

1.  **Read Stage (Производитель):** Один поток читает изображения с диска и помещает их в первую очередь (`readBuffer`).
2.  **Convolve Stage (Потребитель/Производитель):** Пул потоков (по количеству ядер процессора) извлекает изображения из `readBuffer`, применяет к ним операцию свёртки и помещает результат во вторую очередь (`processedBuffer`).
3.  **Write Stage (Потребитель):** Один поток извлекает обработанные изображения из `processedBuffer` и сохраняет их на диск.

```
[Disk] -> [readBuffer] -> [Thread Pool] -> [processedBuffer] -> [Disk]
```

`System.Collections.Concurrent.BlockingCollection<T>` используется в качестве буфера между стадиями и обладает двумя важными свойствами:
*   Гарантирует безопасный обмен данными между потоками.
*   `BoundedCapacity`: Если `readBuffer` заполняется, `Read Stage` автоматически блокируется, не давая "забить" всю оперативную память необработанными изображениями. Это создаёт механизм **обратного давления (backpressure)**.

## Анализ производительности

Бенчмарк был проведён на наборе из **10 изображений размером 4096x4096 пикселей**.

### Огромное выделение памяти

Первый запуск бенчмарка с параллельной реализацией выявил проблему, с которой мы встречались. Бенчмарк был запущен без изменений с последнего статуса Задачи 2. В результате работы занялось `~1.4 ГиБ`, а сам метод был на 200 милисекунд медленнее последовательного

### `ThreadLocal<T>`

Проблема была решена с помощью `ThreadLocal<T>`. Этот позволяет создать один буфер для каждого потока, который затем можно повторно использовать для всех последующих строк, обрабатываемых этим потоком.

### Итоговые результаты

После исправления проблемы с памятью, были получены следующие результаты:

| Метод                                       | Среднее время | Выделено памяти | Ускорение |
|:--------------------------------------------|--------------:|----------------:|----------:|
| Streaming Pipeline (Sequential Convolution) |     2.299 сек |         2.53 МиБ | **1.00x** |
| Streaming Pipeline (Parallel Convolution)   |     1.839 сек |        14.73 МиБ | **1.25x** |

### Выводы

1.  **Проблема с памятью решена:** Главное - сокращение выделения памяти в параллельной версии на с 1443 МиБ до 14.7 МиБ при сохранении корректности и скорости в нестриминговом режиме

2.  **Ускорение не соответствует ожиданиям:** Несмотря на высокоэффективную параллельную свёртку, общее ускорение конвейера составило всего **~1.25x**. Причина может быть связана с внешними факторами в виде скорости сохраненияи и записи изображений

### Итоговый вывод по Задаче 3

Реализованная конвейерная архитектура является гибким решением для потоковой обработки. Получилось найти и устранить bottleneck, планируется исселдовать причины недостаточного ускорения
